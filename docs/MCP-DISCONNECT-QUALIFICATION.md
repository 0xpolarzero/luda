# MCP stdin disconnect during a started mutation

MCP-08 requires “Client disconnect: resources cleaned and outstanding mutation
not silently retried.” `tests/live_mcp_disconnect.py` exercises actual stdin EOF
against the real stdio server after independent evidence that mutation has begun.
It does not send `notifications/cancelled`, cancel an SDK request, kill the tested
server, or merely close an idle client context.

The fixture speaks newline-delimited JSON-RPC over an actual MCP subprocess,
performs initialization, and calls public desktop tools. It closes the request
pipe to deliver EOF. The output pipe remains drained solely to observe whether a
late response exists; this is a tested stdin-disconnect boundary, not a claim
about simultaneous broken stdout, SSH network loss or every client transport.
Server-side task cancellation in response to EOF is allowed; no protocol
cancellation is generated by the test.

## Independent mutation-phase evidence

The keyboard case requests twenty `a` key presses. Before EOF, a separate raw
Xlib `XQueryKeymap` oracle observes an actual down key while the MCP response is
still pending. Native guardian/injector process identities are recorded from
`/proc`, including process start times. No injector is paused or killed to create
this condition.

After EOF, the real server exits, those helper identities disappear, and the
independent X oracle reports no held keys or mouse buttons. The GTK buffer retains
one character in the measured runs; the remaining repeats do not arrive. The
assertion permits observed partial delivery within the one-request count, rather
than requiring input already delivered to disappear. A fresh actual MCP subprocess
has no old operation history, leaves the buffer unchanged before explicit input,
and adds only the separately requested `z`.

The second case invokes a native GTK button. Its callback atomically persists
`started=1, completed=0`, then waits on a bounded test gate. That independent
application state establishes that the action handler has started before stdin
EOF. The harness releases the fixture gate only after EOF; the delivered handler
finishes once, with `completed=1`. This **late effect is expected and recorded**.
Disconnect is not undo. The old server and captured helpers still exit. A fresh
MCP process does not replay the action; a separately explicit invocation is the
only action that increments both counters to two.

The gate controls only the owned test application's delay. It neither substitutes
for the production provider nor marks the server's request phase. Application
state, physical key state and process lifetime are independent of tool-reported
success. Forced server termination during harness cleanup is a failed case, not
silent successful cleanup.

## Results and bounds

All ten assertions passed in three private ordinary-UID runs. The first two used
the same immutable source and took 4.881 and 4.799 seconds. After making any forced
harness cleanup explicitly fail the suite, the final run passed in 4.818 seconds
with unchanged source fingerprint
`fb67fc45fd6fc2d3fbc58de35b8776712764aa3d20f70513babbb9779ba18484`.
It observed keyboard cleanup/server exit 0.229 seconds after EOF and action-server
cleanup in 0.106 seconds. Both server exits were zero; no forced shutdown occurred.
The matrix found no surviving owned processes.

Retained evidence is under
`artifacts/qualification-matrix/run-1789873944184891082/`,
`run-1789874006146203028/` and `run-1789874051145283800/` in the qualification
worktree. The fixture saves metadata-only case results, synthetic application
state and server stderr. No runtime fix was needed. Catalog acceptance, priority
and qualification remain unchanged.

Run as the ordinary desktop user:

```sh
.venv/bin/python scripts/qualification_matrix.py --suites mcp-disconnect
```

The runner supplies private Xvfb, D-Bus, XFWM and XDG state. The test bounds each
mutation/exit wait and checks new sessions on that same private desktop. It does
not qualify display-server failure during disconnect, indefinitely blocked native
cleanup, concurrent human input, persistent recovery across arbitrary transport
loss, or all applications' late callbacks. Existing protocol-cancellation and
owned-input recovery suites remain separate evidence.
