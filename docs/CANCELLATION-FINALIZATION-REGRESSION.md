# Waiting for cancellation finalization before recovery

The integrated clipboard run on `00c6aae` (`run-1789896298246433327`) passed its actual model-update barrier and owned-browser process cleanup, then tried opening a new browser while the cancelled request still held the server operation slot. The new request correctly returned `BUSY`, effect none, in 0 ms. The whole suite failed after 60.009 seconds; this was not the separate hosted 180-second suite-budget issue. Original cases, timings and logs remain under `tests/evidence/cancel-finalization/`.

Process death does not prove server finalization. `execute` releases the operation gate before appending its final history event, while `execute_async` clears cancellation quarantine after its worker finishes. The fixture now captures baseline operation IDs before starting input. After the actual first-segment barrier, cancellation and confirmed descendant cleanup, it releases the bounded application barrier, awaits the real cancellation response and polls **read-only** `desktop_status`. Recovery requires exactly one new `type_text` event with `CANCELLED`, uncertain effect and `ok:false`, plus `recovering:false`. There are no other mutations in this interval. Only then is one new browser-open request issued.

No open retry, guessed settling sleep, synthetic completion response or production change was introduced. A lost cancellation receipt, absent/ambiguous final event or uncleared quarantine fails the fixture. The response wait is bounded to 3 seconds; history polling has a 5-second deadline with the existing bounded per-call transport. The original application barrier retains its independent 12-second limit and `finally` release.

Three focused tests require the fresh final event and cleared recovery, reject old/unrelated completion, and reject non-cancellation or ambiguous history. The private ordinary-UID Xvfb/D-Bus run `run-1789896558085269534` passed all 51 assertions in 67.718 seconds with unchanged source and no owned survivors. It retained the real cancellation response and finalized history, then opened one fresh browser and verified no replay followed by one explicit recovery request. Exact original and corrected run records are compressed alongside this document's evidence. This qualifies the fixture ordering in that local run, not arbitrary external activity or every lost-client scenario.
