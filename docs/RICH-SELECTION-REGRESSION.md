# Rich-editor selection regression investigation

Hosted runs 35499802558 (`037c3cc`) and 35499926123 (`7783721`) failed while the clipboard suite prepared a fresh editor using ordinary native whole-field replacement. Both returned `SELECTION_UNVERIFIED`, effect uncertain, after roughly 1.27 seconds; one followed the multiline-middle case and the other the third case. Original failure logs and application oracles are retained under `tests/evidence/hosted-rich-selection/`.

The previous response did not distinguish synchronization of the requested selection from caret verification after content input. The last completed application POST showed the reset model and initial caret, but asynchronous oracle delivery means that this **does not conclusively identify the failing stage or prove that no input occurred**. The exact hosted scheduling cause remains unconfirmed.

The clipboard increment had changed whole-field/end selections from their established browser-native Ctrl+A/Ctrl+End route to DOM range mapping whenever the updated bridge was installed. The narrow correction restores native shortcuts for those two cases and retains model-bound DOM mapping for genuinely interior ranges. Empty 0..0 collapses at the end rather than creating an AllSelection. In the pinned ProseMirror keymap, Ctrl+A updates the model selection directly. No selection or mutation is retried and the verification deadline/assertions are unchanged.

Errors now include an allowlisted, payload-free `provider_stage`: `selection_sync` means the requested selection did not synchronize; `caret_readback` means native rich input reached the post-content caret check. Both remain honest uncertain errors when input may have happened. Unrecognized stage values are omitted, including provider-supplied text or objects. Agents should inspect current state rather than replaying an uncertain content request.

## Local investigation and regressions

Four diagnostic runs did not reproduce the hosted failure: forty fresh documents (8.527 seconds), forty UI-remounted editors (17.797 seconds), and two forty-case scheduling experiments (20.180 and 20.357 seconds). Each included normal and sixfold renderer CPU throttling. The latter experiments instrumented the pinned editor's actual delayed focus callback and a bounded task after DOM selection; the final experiment delayed that callback from 20 to 50 ms. These are explicitly synthetic scheduling observations, not proof of the hosted cause or generic editor qualification. The pinned view's `input.ts` focus handler schedules a 20 ms selection restoration, but observing that code is only a hypothesis about the original failures.

Five focused regressions verify native whole/end/empty dispatch, unchanged interior mapping, distinct failure stages and actual protocol redaction of unknown stages. The 28 existing rich tests also pass. The native-rich MCP regression passed in 23.044 seconds (`run-1789894131286904710`). The same run's clipboard suite retained a real fixture precondition failure: native Ctrl+End scrolled the 128-paragraph editor, making a later top-of-page reset button non-showing. The accessibility guard correctly refused it. The fixture now returns through public Ctrl+Home and observed native scrolling before requesting that reset, and verifies that scrolling preserved the model.

The corrected clipboard workflow passed all 47 assertions in 60.898 seconds (`run-1789894316433608549`), but that matrix result is **not an immutable-source pass**: hosted evidence files were added during the run. Runtime/test code stayed unchanged; the runner nevertheless correctly returned `source_changed` and exit 1. That result is retained rather than relabeled. A clean frozen-source confirmation is recorded separately after completion.

The next frozen-source run (`run-1789894447324623236`, 60.558 seconds) passed the selection, text, scrolling and composition checks, then failed the later cancellation fixture with `BROWSER_ALREADY_OPEN`. Its retained result exposed an empty “partial” value: the fixture had accepted a stale nonempty oracle from before the verified clear as proof that the new insertion began. It did not independently await the cleared model. This is a separate cancellation-test precondition defect; no full clipboard-suite pass is claimed from that run. The selection correction is committed separately while the cancellation proof is repaired.

The separate cancellation repair now waits for the independent empty baseline, then arms a visible **test-application-only** barrier. After `view.updateState` applies the next document change, a synchronous loopback request supplies the actual model/DOM snapshot and blocks the renderer. The handler has an independent 12-second bound. Only after observing exact `segment-0` does the harness cancel the in-flight request. It verifies the previously recorded descendant PID/start identities are gone before releasing the barrier and opening a new browser; any already returned response is preserved. This does not infer execution from an unresolved client future or stale asynchronous POST, and it does not introduce a production input hook.

Frozen-source run `run-1789894888521599405` passed all 49 assertions in 60.831 seconds. The barrier captured actual model and DOM `segment-0`; the response was `Request cancelled`, recorded process survivors were empty, and the new session had its original document without replay. A subsequent explicit recovery request passed. Compressed original failure and corrected run evidence are retained in `tests/evidence/rich-cancellation-barrier/`. This local result does not establish the original hosted selection failure's exact scheduling cause.
