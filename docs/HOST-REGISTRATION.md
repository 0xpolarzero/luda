# Explicit host-profile registration

This developer/CLI utility builds a VM-specific tool-and-skill plugin, then
explicitly registers it in a selected **host** Codex profile. It is not a Silo
UI action and does not configure Codex's SSH workspace/executor association.
It requires Python 3.12 and a host Codex CLI with plugin commands (tested with
0.155.1). Do not assume Python or the CLI is installed in a Mac app environment.

The transport is ordinary host OpenSSH stdio to one fixed VM. The supplied private
SSH configuration should be generated by Silo's
`editor.rs::prepare_private_transport`, including pinned host keys and the
`msb ssh serve --stdio --no-start --no-inactivity-timeout` proxy. This utility
does not create keys, authorize a connection, modify `~/.ssh/config`, start a VM,
or enable `experimental_environment=remote`. A plugin remains bound to its
selected VM even if a Codex thread uses a different remote executor.

## Build, then explicitly register

Supply an immutable VM UUID, a persistent host marketplace directory, the
matching skill artifact obtained from the verified guest release, and its trusted
expected SHA-256. A hash supplied alongside untrusted bytes establishes no trust.
The utility compares bytes and refuses mismatches; it does not fetch or execute
commands from a guest-provided configuration.

```sh
python3 scripts/build_plugin.py \
  --marketplace-root /absolute/persistent/silo-luda-marketplace \
  --prefix /opt/luda --user silo-desktop \
  --vm-id 00000000-0000-0000-0000-000000000001 \
  --skill-file /absolute/verified/SKILL.md \
  --skill-sha256 <trusted-release-skill-sha256> \
  --ssh-executable /usr/bin/ssh \
  --ssh-config /absolute/private/ssh_config --ssh-alias silo-selected-vm

python3 scripts/register_host_plugin.py \
  --marketplace-root /absolute/persistent/silo-luda-marketplace \
  --codex-executable /absolute/path/to/codex \
  --codex-home /absolute/selected/codex-profile
```

Replace the illustrative UUID and paths with the intended VM/profile. Execute
registration as the profile owner; the existing profile directory must be owned
by that account and not writable by other accounts. There is no implicit profile
or output directory. The builder preserves existing destinations. It packages
verified skill bytes unchanged and derives distinct plugin/marketplace names
from the VM UUID. The MCP server key is `ld-<full UUID without hyphens>`,
independently unique across VMs. Codex CLI 0.155.1 flattened two plugin-local
`luda` keys into one resolved server in the retained initial probe; distinct
plugin names alone did not separate servers. Its cache version includes
transport/skill content identity.

The generated MCP command passes host arguments without a shell and separately
quotes every token of the fixed guest `luda-session` command for OpenSSH's remote
shell boundary. Batch mode and strict host-key checking are explicit; agent and
X11 forwarding are disabled. The guest launcher joins the selected desktop as
`silo-desktop`; it is not host GUI control. Transport files remain external to
the cached plugin and must stay at their declared paths. Update/remove the plugin
when those paths, VM identity or guest skill/runtime release change.

Registration invokes actual CLI marketplace-add/plugin-add/list commands. It
verifies cached launch configuration and skill hashes plus the effective
`codex mcp list --json` command/arguments, preserves unrelated
settings, and refuses a conflicting marketplace, disabled existing plugin or
modified cache instead of overwriting it. It records ownership and attempt state
under the selected profile's `luda-registrations/`, with a cooperative utility
lock; this does not lock unrelated Codex processes out of their own settings.

`registered` and `already_registered` mean the selected profile's cached artifacts
and resolved configuration matched. They do not prove MCP startup, a running guest, tool approval, skill
loading in an existing conversation, or Mac remote-executor placement. Start a
new conversation, inspect doctor/identity information and observe the intended
VM before input. Registration returns the VM UUID and server name, and the
plugin display name/description identify that VM. Each bundled skill keeps the
name `luda` and unchanged generic guidance; duplicate skill names are not routing
identities or authority to choose a VM. Select the intended VM-specific tool
server explicitly. No approval policy is silently replaced by this utility.

## Partial results and updates

An interrupted/failed mutating CLI stage returns `unconfirmed` and leaves its
receipt and any successfully added marketplace/plugin intact. No automatic
rollback or second plugin-add occurs. Re-running can confirm an installation
that actually completed despite a lost response. An incomplete attempt returns
`previous_attempt_requires_review`; inspect that profile with `codex plugin list
--json` and `codex plugin marketplace list --json`. Complete or remove the exact
owned entry deliberately through Codex's CLI after inspecting the outcome.
Receipt reset/removal is an explicit administrative action after that review,
not a retry side effect. A changed bundle/version requires an explicit update
workflow; this first layer deliberately refuses in-place replacement.
