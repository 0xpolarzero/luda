# Temporary screen recording

`desktop_recording(action="start", max_seconds=30)` records the selected X11 display with optional local FFmpeg and ffprobe. It returns a session ticket after the first captured frame. It does not mean the file is complete. Use `stop` with that `recording_id`, or poll `status` after the duration limit. Only `state="complete"`, `playable_verified=true` returns a path after stream inspection and full decode. Failed capture returns no playable-file claim. A finalizing result needs another status check.

The fixed profile is silent MP4, 10 fps, at most 1280×720, with a 1–60 second requested duration. Native displays above 32 million pixels are refused. Each file is limited to 64 MiB by the worker's file-size resource limit; the backend reserves at most 128 MiB including a new capture and retains at most four tickets. One cooperating recorder per account/display can capture at a time. No audio, network service, cloud credentials, screenshots in default logs, overwrite option or arbitrary output path is involved. `doctor.recording.available` reports executable presence; unavailable recording does not make other tools unready. Codec support is checked by actual capture, not inferred from executable presence.

Files and containing directories are private temporary artifacts. Copy a completed file elsewhere explicitly before backend close/reconnect if it must survive. `delete` stops capture and deletes only the original recorded inode. User-added files and replacement files are preserved. Backend close/reconnect and ordinary server death stop the owned worker and remove its temporary artifact. Stop/status/delete remain available while paused or recovery blocks ordinary input. They do not resume the desktop. There is no guarantee of cleanup after machine failure, filesystem failure, or simultaneously freezing the cleanup supervisor and killing its controller; a frozen supervisor cannot process EOF until resumed. The API does not authorize deleting unrelated files to recover space.

Layout is compared using bounded isolated X11 probes approximately every 0.5 seconds and again before validation. Detected topology changes invalidate and delete the partial capture. This sampled check does not prevent changed-layout pixels from briefly entering the temporary file. Video content itself is expected to change. Capture covers the whole selected display, including any visible private content; recording is never started by default.

Implementation uses FFmpeg's [X11 capture device](https://ffmpeg.org/ffmpeg-devices.html#x11grab), with explicit duration and resource limits. FFmpeg and ffprobe are optional test/runtime capabilities, not mandatory installer dependencies.

## Scoped evidence

On Ubuntu 24.04 ARM64, FFmpeg 6.1.1, ordinary UID1001 private Xvfb 900×650, `tests/live_recording.py` passed four checks: actual MCP start/stop with independently decoded red then green rendered frames (15 frames, 50,597 bytes), stop/delete while paused preserving an added user file, automatic duration completion, and connection-close deletion. `tests/live_recording_faults.py` passed five checks: competing backends, actual `RLIMIT_FSIZE` failure, stopped-supervisor deletion and worker exit, detected logical-monitor change, and owner SIGKILL cleanup. This file-size quota is not an actual full filesystem test; an injected pre-spawn ENOSPC unit test separately covers typed storage refusal.

Development failures are retained in `/workspace/luda-recording-faults.log` and `-2.log` through `-5.log`. The initial bare Xvfb reset its generation between clients; adding the fixture's owned WM resolved that fixture setup error. The monitor-change probe then exposed absent RandR event delivery; the implementation now uses bounded topology reads and the same probe passes. The first successful MCP log is `/workspace/luda-recording-live.log`; the post-fix run is `/workspace/luda-recording-live-2.log`. These are local development evidence, not macOS/Silo, codec portability, long stress, audio, or general recording qualification.
