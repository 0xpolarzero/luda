# Hosted clipboard-suite timeout

Hosted source `9e17932` reached the matrix's 180-second whole-suite limit after 37 successful assertions and 279 processed public tool calls. The last assertion was `scroll-preserves-limit-model`; the latest asynchronous oracle showed the subsequent fresh editor, not focused. There was no Python exception or identified slow-call traceback. The original suite log, MCP log, model oracle, cases and matrix result are retained under `tests/evidence/hosted-clipboard-suite-timeout/`.

This evidence alone cannot distinguish cumulative runtime from a stalled final call. The fixture now appends payload-free monotonic request-start/end records, tool names, request indices, durations, fixed error codes and backend elapsed times. Each case is timestamped. It also wraps the complete write/drain/response coroutine with a 16-second watchdog; the existing 15-second response deadline is unchanged. Input strings, element IDs and clipboard contents are not written to this timing log. The cancellation request retains its separate actual-application barrier and owned-process deadline.

Local immutable run `run-1789895927934385067` (source `0a62480` plus timing instrumentation) passed all 49 assertions in 69.420 seconds, with no owned survivors. Its 305 ordinary request/response calls totalled 66.632 seconds; the longest took 0.674 seconds. Assertion37 completed at59.678 seconds. Request279 was the subsequent `desktop_focus_element`, completed locally in0.146 seconds. This alignment is useful evidence, not proof that the hosted request completed or that it was the only remaining in-flight action.

The29 content results retained by both runs totalled8.498 seconds locally and28.303 seconds hosted (3.33×). This supports cumulative hosted latency as a plausible explanation for exhaustion of the whole-suite budget. It does not justify weakening per-operation verification, replaying failed input or treating the original timeout as passed. The16-second wrapper was added after that immutable run to include the previously unbounded write/drain portion; the recorded run predates this additional fixture-only outer watchdog.

One local setup command initially failed before launching a display because the fresh worktree lacked an ordinary-user-writable artifacts directory. Creating that dedicated directory corrected setup; it was not an application retry. No production runtime timeout changed.

The clipboard suite now declares a300-second default whole-suite watchdog to accommodate its305+ sequential calls on the measured slower hosted environment. Every other suite retains180 seconds. An explicit `--timeout` still overrides either default within1..300 seconds; suite metadata is clamped to this bound. The effective watchdog is recorded per run. Focused tests cover the one-suite default change, explicit override/rejection and metadata clamp. This bounded test budget change does not relabel the original failure; the next hosted trace must still show where time is spent.
