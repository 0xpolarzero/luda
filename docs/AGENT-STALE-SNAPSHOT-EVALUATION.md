# First-attempt stale screenshot recovery

This single fresh-agent task exercises **INTEL-05**: “Stale snapshot: agent reobserves and recomputes coordinates.” It uses an owned GTK canvas with three harmless parcel labels and Commit. The prompt asks only to choose Amber, commit once, and verify; it does not disclose a move or recovery sequence. The canvas exposes no semantic tile/button actions. Its independent app-written oracle records every received click and the selected label/commit count.

A test-only stdio MCP relay starts the unchanged Luda server. After its first successful screenshot response, the relay moves only the fixture PID's Parcel Board window using external `wmctrl`, waits for independent `xwininfo` displacement, and forwards the original response byte-for-byte. The screenshot and snapshot identity are real; the move makes that snapshot stale before client delivery. No fabricated error, image, stale flag, production hook or agent action is injected. The relay does not move any subsequent observation. This models a precisely timed external window move rather than claiming to reproduce every spontaneous layout race.

## Reproduction and limits

Run `sudo .venv/bin/python scripts/agent_stale_eval.py --timeout 180` only with explicitly authorized existing CLI authentication; it consumes model usage. The CLI uses its existing account, while desktop, relay and MCP run as UID 1001 with private Xvfb/D-Bus/XDG and no shared desktop or global configuration changes. `tests/agent_stale_fixture.py` is the independent canvas and `tests/stale_snapshot_relay.py` is the external orchestrator. Four unit tests cover exact intended clicks, absent-stale refusal, new snapshot plus changed coordinates, and unrelated-window/nonimage filtering.

This is one first-attempt outcome, not a success-rate estimate or qualification for arbitrary moving apps, dynamic canvas content, replacement-window generations, or macOS/Linux. The relay's PID/title check and xwininfo proof operate only on its own disposable fixture; they are not a new production window-identity mechanism. The root agent is constrained by task instructions and trace grading, not an adversarial filesystem barrier. Original full compressed trace/result plus before/after screenshots remain retained. No production runtime or release qualification status changed.
