# Installed applications

`list_applications(query='', limit=50)` searches visible installed desktop entries by case-insensitive ID, display name and description. Results contain stable `application_id`, display text and file/URI capabilities, plus `total_matches` and `truncated`. Limits are 1–200. Hidden entries and entries without an executable or D-Bus activation are excluded. Discovery does not change defaults or install applications.

`launch_application(application_id, files_or_uris=[])` accepts a listed desktop-entry ID, never an executable command or desktop-file path. Unicode and spaces in legitimate IDs are preserved. Inputs are absolute existing local files/directories or explicit URIs, capped at 128 items and 64 KB combined. Relative paths, nonexistent local files, control characters, invalid percent escapes, remote file:// hosts and malformed HTTP URIs are rejected. File-only desktop entries reject remote URIs; entries declaring no input support reject inputs.

The helper uses system PyGObject/Gio and `Gio.DesktopAppInfo.launch_uris_as_manager_with_fds`. Gio interprets desktop-entry Exec placeholders and quoting. There is no shell construction or custom `%F`/`%U` substitution. Gio may deliver a local file URI as a filesystem path even with `%U`; this is native desktop-launch behavior, not a guarantee that URI spellings reach argv unchanged. Remote URIs remain URIs. Installed desktop entries may themselves invoke shells; Luda neither edits their commands nor interpolates input into shell text.

New child processes receive /dev/null for stdin/stdout/stderr and their own session, preventing application output or lifetime from retaining MCP pipes or joining helper cancellation's process group. The launch context sets ACCESSIBILITY_ENABLED=1 and QT_LINUX_ACCESSIBILITY_ALWAYS_ON=1, and removes NO_AT_BRIDGE. These apply to newly spawned processes; an existing singleton or D-Bus-activated process cannot have its existing environment changed retroactively. Browser-specific accessibility behavior still requires application qualification.

The five-second helper inherits operation cancellation/deadlines. Accepted launch returns `effect: dispatched`, the application ID, and only PIDs actually reported by Gio's spawn callback. Empty PID hints are valid for singleton/D-Bus launches. A PID does not establish readiness, a created window or successful file loading; observe the desktop afterwards. Launch is not automatically retried. Cancellation or failure after activation may leave an application running; inspect before retrying. Existing singleton apps are not signalled by this API.

## Evidence

`tests/live_application_launch.py`, run as ordinary desktop uid 1001 under the shared live-test lease, creates entries only in a temporary XDG_DATA_HOME. Three GTK fixture launches independently recorded exact argv, including Unicode, spaces, percent signs, shell metacharacters, `%F` multiple files and `%U` remote/local inputs. The test verified actual windows, correct uid, separate sessions, /dev/null stdio and accessibility environment. Missing/broken entries, missing files and unsupported inputs were rejected. A pre-cancelled launch left existing fixture apps alive. Tests terminate only their own fixture processes and never modify the user's registry.

Ten unit tests cover input validation, local URI encoding, malformed URI rejection, Unicode IDs, bounded helper failure, malformed replies and preserved no-effect errors. Additional private-bus tests below qualify terminal entries and D-Bus singleton routing. Flatpak/Snap wrappers remain unqualified.

`tests/live_application_services.py` uses a private session bus and temporary service registry. A Terminal=true entry executed inside an independently observed terminal window. A Gtk.Application singleton was activated and then received the exact requested file URI in the same process; empty spawn-PID hints correctly represented D-Bus activation. A deliberately slow open request exceeded the helper operation deadline: the existing singleton stayed alive and independently recorded the delivered request, demonstrating why timed-out launches must not be retried blindly.

Gio performs D-Bus activation asynchronously even when its launch function returns success. The helper therefore waits, boundedly, for AppLaunchContext's launched/launch-failed signal before exiting. This verifies desktop-service acceptance, not application readiness. Helper stderr and Gio exception text are redacted so launch arguments are not echoed in errors.

## Agent tools

The MCP tools are `desktop_applications(query, limit)` and `desktop_launch(application_id, files_or_uris, wait_timeout=1)`. Discovery is observational and remains available while cooperating agent input is paused; launching uses the existing transaction, pause guard, operation deadline, cancellation and status history. After a dispatched launch, use `desktop_windows` to find the new or existing application. No new window or process is promised for singleton applications.

`tests/live_mcp_applications.py` exercised a real stdio MCP client/server: schema discovery, application search while paused, blocked launch while paused, resumed launch, independent Unicode argv readback, subsequent visible window and recorded dispatched operation history. Missing applications returned a structured error. Test cleanup restores the prior control state.

## Optional launch-window observation

`desktop_launch` observes windows for a requested interval of 0–3 seconds after one accepted launch (default 1; 0 returns dispatch only). `spawned_processes` captures same-UID PID/start generations inside Gio's direct-child callback, before those child PIDs can be reaped and reused. Already-exited children are reaped without waiting for application lifetime; surviving applications are not killed on helper exit. The Python `launch_application` function remains dispatch-only.

`window_observation` reports `one_candidate`, `multiple_candidates`, `pending`, `unassociated`, `unavailable`, or `not_requested`. Candidates include only current windows matching captured PID/start generations. There are at most 50 candidate rows, with an explicit observed count and truncation flag. Incomplete enumeration reports `unavailable` even when a candidate exists, so missing metadata cannot establish uniqueness. A launch without a captured generation, including D-Bus/singleton activation, is `unassociated`; titles and old PID hints are never used to guess. Inspect the returned window IDs to choose the intended window.

A splash and requested document can share one process; neither one candidate nor several verifies the requested file loaded or that a window is ready. The wait is an observation interval, followed by any in-flight enumeration within the shared 12-second MCP operation deadline (the launch helper has its own five-second cap). Cancellation and post-dispatch failures retain possible effects; nothing is relaunched or replayed. A non-cancellation enumeration failure returns dispatched with unavailable observations.

`tests/live_launch_observation.py` uses actual stdio MCP, temporary desktop entries and ordinary-UID private GTK/Xvfb/D-Bus. Independent fixture PID/start, window and append-only launch oracles check an immediate decoy plus delayed document in one process, a short pending wait and explicit dispatch-only launch. Each request starts once. Owned applications are terminated and reaped. Focused units additionally cover PID reuse, incomplete and truncated enumeration, sanitized enumeration failure, cancellation, shared deadline and invalid waits before dispatch. This qualifies process-bound observation, not application-specific document readiness or singleton association.
